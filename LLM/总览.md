LLM 底层原理
Transformer 的注意力机制（Attention Mechanism）：
思想：关注一句话中某些关键词部分； 核心总结是让模型在处理某个词时，能够“关注”输入序列中其他相关的词，并根据重要性加权融合它们的信息。
自注意力机制（Self-Attention）：每个词都与其他所有词（包括自己）计算相关性
多头注意力（Multi-Head Attention）：使用多组（多个“头”），每个头学习不同的注意力模式（如语法、语义、指代等），然后将结果拼接并线性变换


function_call
结构化解码器（Structured Decoder）：
1、基于文法约束的解码：在生成每个 token 时，只允许模型从“合法候选 token”中选择，这些候选是由当前上下文 + 目标 Schema 组成.
技术原理：
1、将 JSON Schema 编译成一个 有限状态机（Finite State Machine, FSM） 或 上下文无关文法（CFG）
2、每生成一个 token，就更新 FSM 状态
3、只保留能使 FSM 转移到合法状态的 token （在 logits 层屏蔽非法 token（logit mask））
优点：输出绝对合规
缺点：增加推理延迟（每步都要计算 FSM）

LLM 大模型的KV cache缓存时间是多少？KV_cache的可设置的缓存时间是多少
LLM的KV Cache**没有固定的缓存时间**，其生命周期完全和用户请求、模型推理机制强绑定，会随推理过程动态变化，当满足特定条件时就会被释放或替换，具体可结合推理流程、框架机制和实际场景分为以下几种情况：
1.  **单轮请求内：随token生成动态存续，请求结束即释放**
    这是KV Cache最基础的生命周期模式。在用户发起一次文本生成请求时，KV Cache会从无到有逐步构建，且全程伴随该请求的推理过程：
    - 生成第一个token时，模型会计算输入提示词对应的Key（K）和Value（V）矩阵并缓存；
    - 后续每生成一个新token，仅计算新token的Query（Q）矩阵，同时将新token的K、V向量追加到缓存中，供下一个token生成时复用；
    - 当本次请求完成所有token生成（比如生成一篇短文、回答一个问题结束），该请求对应的KV Cache就会被释放，避免占用GPU内存。
2.  **多轮对话场景：跨轮复用，会话终止后释放**
    在聊天机器人等多轮对话场景中，KV Cache会跨请求复用，生命周期延长至整个会话结束。例如用户和模型连续对话时：
    - 第一轮提问生成回答后，KV Cache会保留该轮的对话token对应的K、V数据；
    - 第二轮用户基于上一轮内容追问时，模型无需重新计算上一轮对话的K、V，直接复用缓存数据，仅计算新提问的相关矩阵，既能减少延迟，又能保证对话上下文的连贯性；
    - 当用户关闭会话窗口、会话超时，或者达到模型设定的最大上下文长度时，这一整个会话对应的KV Cache才会被清理。
3.  **框架优化下：可被临时交换，需时重新召回或重计算**
    像vLLM这类采用PagedAttention等优化技术的推理框架，会对KV Cache做更灵活的内存管理，其生命周期可能出现“临时离开GPU内存”的情况：
    - 当GPU内存紧张时（比如同时处理大量并发请求），框架会将部分暂时不生成token的请求对应的KV Cache块交换到CPU内存中暂存，释放GPU资源供其他高优先级请求使用；
    - 当该请求需要继续生成token时，若缓存块还在CPU，会重新将其召回GPU；若缓存块已被清理，模型则会通过重计算的方式重建对应的KV Cache，以此平衡内存占用和推理效率。
4.  **超长序列场景：滑动窗口机制下，仅保留近期token缓存**
    对于Llama 2等支持滑动窗口注意力机制的模型，KV Cache不会无限累积，而是会动态丢弃过期的缓存数据。比如模型设定滑动窗口大小为2048个token时：
    - 当生成的token序列长度超过2048后，模型仅保留最近2048个token对应的KV Cache，更早的token缓存会被自动丢弃；
    - 这种情况下，KV Cache的生命周期以“窗口内的token序列”为单位，始终维持在设定的窗口长度范围内，既控制内存占用，又能保证近期上下文的关联性。
